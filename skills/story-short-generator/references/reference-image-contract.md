# 参考图形态契约（档位 × 参考图实测）

> 本文件是「参考图形态门禁 G-ref」的完整依据。SKILL.md 只留压缩版与指针，**证据与结论强度以本文件为准**。

## 1. 结论

**成片出不出角色副本 / 画面污不污，取决于档位钉死的「采样配置」（步数 + 采样分辨率），与实现家族无关。**

- **`fast` 档**（4 步 Lightning · 832 长边）：几乎任何**多主体**参考图都会泄漏。泄漏**样式不固定**——可能是多出人，也可能是内容被投影成背景墙纸，或环境被换掉材质。故 `fast` 档对进 `ref_nodes` 的参考图设**形态门禁**。
- **`balanced` / `quality` 档**（8 步 / 20 步 · 1344 长边）：全部已测形态（含角色卡、一图两身体、三视图、综合设定图）都**只出 1 个角色**，无需门禁。
- **prompt 端压制无效**：在 `detailed_description` 与 `retention_analysis` 里同时写明「只出现一个」类约束，`fast` 档**照样出 5 个**。唯一解法是参考图形态或档位。

### 由本结论导出的现行产品规则（形态分档）

**角色卡的默认形态跟着项目视频档位走**（STEP 0 选定、`canvas_set_state(mode=…)` 持久化）：

| 项目视频档位 | 角色卡默认形态 | 依据 |
|---|---|---|
| `fast` | **单视图正面全身**（一图一人、纯底、零文字） | 本文件 §2 的 fast 行：多主体必漏 |
| `balanced` | **三视图横排**（正 / 侧 / 背全身，1×3，纯底、零文字） | §2 balanced 行：角色卡（4 身体）→ 只出 1 个角色 |
| `quality` | **三视图横排**（同上） | §2 quality 行：三视图（3 身体）→ 只出 1 个角色，首 / 中 / 末帧全干净 |

- **只适用于角色卡**：场景卡、道具卡仍是单视图（多视图对这两类资产在非 `fast` 档未测）。
- **单视图在所有档位都合法**；三视图卡只在非 `fast` 档可用。
- **门禁仍按「每次调用实际传入的 `tier`」判定**：项目档位非 `fast`、某镜临时降到 `fast` 时，该镜的三视图卡立刻不合规（升档或临时补单视图）。

## 2. 实验矩阵

**固定条件**：同一份 H3 官方 Ref2VA 六段式 prompt（逐字相同）· seed `424242`（另注明者除外）· `length=124`（≈5.17s）· 16:9 · 同一场景（审讯室）· 同一角色。

| 档位 / 实现 | 参考图 | 每图主体数 | 成片角色实例 | 其它烙印 |
|---|---|---|---|---|
| fast `minimax-h3-ref2v-fast` | 单视图 | 1 | **1** ✅ | 无 |
| fast | 两张单视图（占 2 个槽位） | 1 + 1 | **1** ✅ | 无 |
| fast | 一图两身体 | 2 | **3** ❌ | — |
| fast | 三视图（正/侧/背） | 3 | 1 | ❌ **两侧墙被换成金色金属板 + 光斑**（参考图竖排分栏结构映射上墙） |
| fast | 角色卡（1 全身 + 3 头部特写） | 4 | **5** ❌ | 卡片分区布局被贴进画面 |
| fast | 角色卡（seed `777333`） | 4 | **5** ❌ | 同上，稳定重现 |
| fast | 综合设定图 | ~15 | 1 | ❌ **整张图投影成墙面** + 中文 caption 烙印 |
| fast | 综合设定图（seed `777333`） | ~15 | 1 | ❌ 同上，更重 |
| balanced `minimax-h3-ref2v-ctx-balanced-pdd` | 一图两身体 | 2 | **1** ✅ | 无 |
| balanced | 角色卡 | 4 | **1** ✅ | 无 |
| balanced | 综合设定图 | ~15 | **1** ✅ | 无 |
| **quality `minimax-h3-ref2v-quality`** | **三视图** | **3** | **1** ✅ | **无 —— 首 / 中 / 末帧全干净** |

### 旁证：旧实验的 fast 臂

`docs/three-view-experiment.md`（本插件仓库）在 `mode=fast`（4 步 Lightning LoRA、832×480）下测过 9 个臂，结论与本表 fast 行一致：

- 三视图原卡 → 多只狐狸；裁掉全部文字后**仍** 3 个角色 ⇒ 重复由**视图数量**决定，与文字无关；
- prompt 声明「只出现一只」→ 仍是多只；
- 正/侧/背**三张单图占 3 个 ref 槽位** → 单只、干净（与本表第 2 行一致）；
- 裁切正面单视图 / `ImageCrop` 预处理 → 干净。

> 该实验**全程只测了 fast 一档**。它没有被证伪，只是缺档位维度——本文件补上这一格。

## 3. 门禁 G-ref 规程

### 触发与判定键

**判定键是「每次生成调用实际传入的 `tier`」**，不是 STEP 0 那一次选择。原因：本流程允许「先 `fast` 走通全片再升档」与「本镜临时改档」，只按 STEP 0 判会漏。

### 判定条件

当 `tier=fast` 时，每个将要进 `ref_nodes` 的图片节点必须**同时**满足：

1. **单主体** —— 画面里只有一个角色 / 一件道具 / 一个环境视角（没有第二个身体、没有剪影、没有镜像）
2. **单视图** —— 不是多格拼图（无三视图 / 四视图 / 表情组图 / 姿势组图 / 多角度场景卡 / 设定图）
3. **零文字** —— 无角色名、无 `FRONT VIEW` 之类标注、无 hex 色值、无 caption、无水印
4. **无拼图** —— 同上第 2 条的视频侧表述：绝不把多张单视图拼成一张

判定方式：用当前模型自身视觉读图核对（当前模型不支持图片输入时回退 `describe_image`）。

### 不通过时的四个出路（出选项卡，**不渲染**）

1. **升到 `balanced` / `quality` 按原图渲染**（推荐——多视图参考图在这两档实测干净）
2. 换成单视图卡（新建或复用）后重渲
3. 用户手动裁图上传单视图
4. 放弃该参考图（纯文本生成）

### 落点

| 位置 | 做什么 |
|---|---|
| STEP 0 | 「生成档位（视频）」选项卡**写明该档对应的角色卡形态**（形态由档位推导，不单独出题） |
| STEP 3 | 角色卡按视频档位出形态：`fast` 单视图 / `balanced`·`quality` 三视图横排 |
| STEP 3 / 4 / 4.5 复用库内资产前 | 按**本次要用的档位**核形态（库里可能存着三视图卡、多角度场景卡、多视图道具卡——三视图卡在非 `fast` 档可用，在 `fast` 档不合规） |
| STEP 5.5 第 11 项 | 规划期预检：`绑定` 列引用的每张卡在**该镜实际档位**下是否合规 |
| STEP 7「渲染前的门」 | 组装 `ref_nodes` 前逐节点判定（**混合档位下最常见的踩线点：非 `fast` 项目里某镜临时降到 `fast`**） |
| 门 3 自检 | `fast` 档镜必须**留痕**写明 G-ref 已过 |

## 4. 结论强度与未解变量

**必须随结论一起给出，不得省略：**

1. ✅ **「档位 vs 实现」混淆已拆开**（2026-10-08 钉实现实验）。原先三档解析到三个不同实现，无法区分差异来自「步数 / 分辨率」还是「实现本身」。用配置面 `pins` 把实现家族钉死后对照，得到完整 2×2：

   | 采样配置 | 非 ctx 家族 | ctx 家族 |
   |---|---|---|
   | **fast**（4 步 · 832） | ❌ **5 个副本** | ❌ **5 个副本** |
   | **balanced**（8 步 · 1344） | ✅ **1 个** | ✅ 1 个 |

   条件：同一张角色卡（4 主体）· 同一份 Ref2VA prompt（逐字）· 同 seed `424242` · `length=124`。
   **⇒ 实现家族不是原因；`fast` 档的采样配置才是。**
2. ⚠️ **仍未拆开：步数与采样分辨率**。这套清单里两者**绑死**——`fast` 恒为 4 步 + 832，`balanced` 恒为 8 步 + 1344，**工具面无法单独改变其一**。所以只能说「fast 档的采样配置（4 步 + 832）是原因」，不能进一步断言是步数还是分辨率。
3. **样本量小**——每格 N = 1~2 个 seed，属**方向性证据**，不是统计结论。
4. **结论绑定当前档位配置**——档位映射到哪个实现由配置决定（设置页的档位选择 / 家族偏好 / 钉实现）。**用户改配置后需重新取证**；门禁本身按 `tier` 文字判定，**不写死实现 id**。
5. **未测**（按新的形态分档规则，这几格直接关系到默认形态的把握度）：**`balanced` 档的三视图横排**（该档已测的是「角色卡 1 全身 + 3 头特写」「一图两身体」「综合设定图」，共性是多主体 + 纯底 + 零文字；三视图本身只在 `quality` 档实测）；**`quality` 档的角色卡（1 全身 + 3 头特写）**；综合设定图在 `quality` 档；**两个不同角色的多槽位**（正常用法，需确认不会被合并成 1 个）；道具卡作 `ref_nodes`（ref 数 >2）；风格锚点作 `ref_nodes`；图内文字对 `fast` 档的独立影响量。

> **钉实现实验的操作口径**（复现用）：`~/.dsh/dsh-short-video-studio.json` 的 `pins[capability]` 可写**实现 id** 或**家族名**；配置**每次调用重读**，所以**不需要重启插件**。注意 pin **不跨档**：钉的是 fast 档实现却请求 balanced ⇒ 直接报错。实验后务必还原配置（备份 + md5 校验）。

## 5. 复现方式

1. 取一张参考卡作身份锚点——复现 `fast` 臂取**单视图**；复现 `balanced` / `quality` 臂取**三视图横排 / 角色卡**（多主体，正是新规则下这两档的默认形态）。
2. 用同一份 H3 Ref2VA 六段式 prompt，只替换 `ref_nodes` 指向的图片节点。
3. 逐档（`fast` / `balanced` / `quality`）固定 `seed` 与 `length`，各跑一条。
4. `extract_frame` 抽**首 / 中 / 末**三帧，逐帧数画面里的角色实例数、检查有无文字烙印与背景污染。

> 本轮实验产物在施工会话的画布上（分组「对照实验」「三视图测试」），含每条视频与抽帧节点，以及诊断用对照拼图（`_final_matrix.png` / `_threeview_compare.png` 等 scratch 文件，非画布节点）。
